# 手 · whalelife-plugin-hands

给 WhaleLife 装上的一双手：列目录、读文件、写文件、跑本机命令。

WhaleLife 主干只负责对话与插件框架，碰不到硬盘。这个插件补上那一层，
让助手能真的动文件、跑 node、查端口——但只在允许的根目录里动。

> **这是高权限插件。** 装上之后，模型可以读写你允许目录里的任何文件、执行任意命令。
> 先读完下面的「边界」一节再决定装不装。

## 工具

| 工具 | 作用 | 危险级 |
|---|---|---|
| `hands_list` | 列目录，`depth` 上限 3；超过按 3 处理并在末尾标注 | safe |
| `hands_read` | 按行读文本文件；头部写明「第 a–b 行，共 N 行」，越界报错，读完与空文件分开报 | safe |
| `hands_write` | 写或追加文本，自动建父目录；覆盖前留副本，可带 `expected_sha256` 版本比对 | 需确认 |
| `hands_run` | 跑 PowerShell 脚本，可带 `verify_files` 写后核验；输出只当轮可见（见坑 7） | 危险 |

## 环境要求

- WhaleLife 宿主，插件 API `1.x`
- Windows（`hands_run` 调 `powershell.exe`；其余三个工具跨平台）
- 不需要其它插件，`depends` 为空

## 安装

### 手动安装

把本仓库的 `index.ts` 和 `plugin.yaml` 放进宿主的插件目录：

```
<宿主目录>/plugins/hands/
├── plugin.yaml
├── index.ts
└── data/            # 首次运行时自动创建
```

然后在控制台「插件管理」里启用 `hands`。
宿主目录就是 WhaleLife 仓库根，`index.ts` 里的 `../../core/context.ts` 按这个位置解析。

### 商店安装

如果本插件已被社区目录收录，可在控制台商店直接安装。
本仓库的 Release 里带有 `.wlpkg.gz` 发行包，发行说明写了大小和 SHA-256。

## 配置

配置文件：`plugins/hands/data/config.json`

```json
{
  "roots": ["D:\\我的工作区"],
  "timeout_ms": 60000,
  "max_output_chars": 20000
}
```

| 键 | 默认 | 说明 |
|---|---|---|
| `roots` | `[]` | 允许操作的根目录列表。**留空时回落到宿主自己的工作目录。** 写 `"*"` 表示不限制，非常不建议 |
| `timeout_ms` | `60000` | 单条命令超时 |
| `max_output_chars` | `20000` | 输出超过这个长度就掐头去尾保留中间提示 |
| `backup_keep_days` | `30` | 覆盖前副本保留天数，过期自动删 |
| `backup_max_bytes` | `1073741824` | 副本目录总量上限，超了从最旧的删 |
| `encoding_prelude` | `false` | 设 `true` 时每条命令前自动加控制台 UTF-8 两行（见坑 10），默认不加 |
| `transient_output` | `true` | `hands_run` 的输出只当轮可见，长期记忆只留一条极简回执。设 `false` 回到「整段输出永久入档」（见坑 7 的代价） |
| `deny_patterns` | 见源码 | 命中即拒绝的命令片段，如 `format `、`diskpart`、`reg delete` |

写进 `config.json` 的键会覆盖默认值；没写的键沿用默认。

## 边界

- **路径闸**：四个工具的每个路径参数都要落在 `roots` 之内，越界直接报错，不静默改成别的路径。
- **拒绝清单**：`deny_patterns` 里的片段出现在命令里就拒跑。这是防手滑，不是安全边界——真要防，靠的是 `roots` 只开一个专门的目录。
- **没有沙箱**：`hands_run` 跑的是你当前用户的权限。它拦不住一个存心使坏的模型，只能拦住"模型不知道自己在干什么"。
- **建议**：单独开一个目录给助手用，`roots` 只指向它；重要的东西放在外面。

## 用法示例

用户说"看看下载目录里有什么"。

```
hands_list { "path": "Downloads" }        // 相对路径按 roots[0] 解析
```

改动文件并当场核验：

```
hands_run {
  "command": "$value = 42; Write-Output \"值=$value\"",
  "verify_files": [{ "path": "out.txt", "contains": ["值=42"] }]
}
```

`verify_files` 会在命令跑完后回读文件，逐条报告哪个字面量在、哪个不在。
说"写好了"必须有这个回执，否则只能说"命令执行过，文件未验证"。

详细用法见 [`docs/使用手.md`](docs/使用手.md)。

## 踩过的坑

每一条都写清**现象 → 原因 → 修补**，方便以后改 `runShell` 时不用重新踩一遍。

### 1. 命令里的 `$value` 被吃掉

**现象**　发 `$value = 42; Write-Output "值=$value"`，回来的是 `值=`，变量像是凭空没了。
长度不报错、退出码 0，就是内容凭空少一段。更糟的是带引号拼路径时，路径静默变成一个残缺的字符串，
命令照样"成功"。

**原因**　原先用 `execFile("powershell.exe", ["-Command", command])`。
`-Command` 的实参要先过一层 Windows 命令行解析，双引号里的 `$` 在 PowerShell 看到之前就被外层处理掉了。
这跟 PowerShell 的引号规则无关，是穿了两层壳。

**修补**　不再拼命令行字符串。每次调用把脚本写进 `%TEMP%\hands-<随机>.ps1`，再用
`powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <那个文件>` 跑。
`-File` 的参数是平面参数，脚本内容不经过命令行解析，`$` 原样进入脚本。

### 2. 中文输出乱码

**现象**　`Write-Output "测试"` 回来是一串 `锟斤拷` 或 `娴嬭瘯`。

**原因**　Windows PowerShell 控制台默认按系统 ANSI 代码页（简体中文是 GBK，如 936）输出字节，
而插件按 UTF-8 解码。麻烦在于**不能无脑"先试 UTF-8、失败再试 GBK"**——「值」的 GBK 字节
（`D6 B5`）恰好也是合法 UTF-8 序列，严格解码不会失败，解出来却是别的字，静默出错。

**修补**　顺序反过来：先严格 UTF-8 解，解出来若落在可疑区段（私用区、替换符、连续高位），
再回退重试 GBK。判不出来的情况下宁可报"编码不明"，也不猜一个像样的结果。

### 3. 临时 .ps1 的 BOM：和配置文件正好相反

**现象**　脚本里写中文注释或中文字符串，`-File` 执行时报解析错误，或者中文变成乱码，
报错信息还指向一个看起来没错的行。

**原因**　Windows PowerShell 5.1 读**没有 BOM** 的 `.ps1` 时按系统 ANSI 代码页解析。
文件是 UTF-8 写的，没 BOM，中文就按 GBK 解释。

**修补**　临时脚本一律写成**带 BOM 的 UTF-8**。注意这条只针对 `.ps1`：
`config.json`、`plugin.yaml`、`.md` 这些配置文件必须**不带 BOM**，否则别的解析器会把 BOM 当成内容。
一个插件里两种规矩并存，容易搞混，所以写在这里。

### 4. 失败的命令返回退出码 0

**现象**　命令明明报了错（红字一大段），回执却是"退出码 0"，于是被当成成功往下走。

**原因**　PowerShell 默认不因为非终止性错误改变进程退出码。走 `-Command` 时，
即使语句报错，进程通常仍以 0 结束。

**修补**　脚本末尾固定追加一行 `if (-not $?) { exit 1 }`。
只要最后一条语句失败，进程就带非零码返回。判断成败看退出码，不看有没有输出。

### 5. 工具抛异常会把整个插件撤掉

**现象**　某次调用里文件不存在，结果**四个工具全没了**，插件页显示异常，只能重载插件。

**原因**　宿主的 worker 包装器把工具抛出的异常视为插件故障，会撤销该插件的全部工具入口。
一处小错，满盘皆输。

**修补**　所有工具函数都过一层 `safe()`：抛出的异常在插件内收口，变成 `错误：<原因>` 的文本返回。
读文件那条也做了区分——只有 `ENOENT` 才算"本来就不存在"，别的读错误必须原样报出来，不能当成空文件。

### 6. 写文件用 PowerShell 重定向，编码不可控

**现象**　`Out-File`、`>`、`Set-Content` 写出来的文件，换行是 CRLF、编码是 UTF-16 或 ANSI，
下游 `JSON.parse` 直接失败。

**原因**　PowerShell 各版本这些 cmdlet 的默认编码不一样，5.1 和 7 不同，重定向 `>` 又是另一套。

**修补**　写文件不走 shell，用 `node:fs` 的 `writeFile` 显式写 UTF-8。
真要由 shell 写，就 `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`。
写完必须回读一次，拿到字节数或行号才算写成。
### 7. 命令输出把长期记忆撑爆

**现象**　跑一次 `Get-ChildItem -Recurse` 或者读一份大日志，接下来几轮对话都吃力，
上下文里全是那段输出；过几天回头，还记得当时屏幕上每一条文件，却记不得为什么跑它。

**原因**　工具结果默认走 `register`，整段返回值进消息历史与记忆。`hands_run` 的输出常常几万字符，
对长期记忆几乎没有价值，有用的只有「跑过什么、成没成」。

**修补**　`hands_run` 走 `registerTransient`：正文只给当轮，持久化只留一条极简回执
（`tool`、`ok`、`exit_code`、`command_head` 前 120 字、`output_chars`、`ms`，有核验时再带三项计数）。
回执是有界 JSON，不抄正文、不抄 stderr、不抄命令全貌。

宿主给的契约是 `{ content, receipt }`：`content` 只对当轮可见，`receipt` 才是入档的那份。
实测一次 44 字符输出的命令，记忆里落下的回执只有 15 字符；同样的命令在旧版是整段入库。

**代价三条，选之前先看清楚**：

1. 只要这一轮调过 `hands_run`，整轮被标成「含临时资料」——工具参数不写进经历，
   独立事实也写不进去。需要记事实的事，放在没跑命令的那一轮做。
2. 写入核验失败后的自动修复请求在本轮不会触发，得下一轮再说。
3. 执行档案里这次调用的 id 变成 `temporary_<hash>`，翻旧账要在归档里按时间对，不能按 id 找。

**换来的**：大输出不再堆积。记忆里每次调用大约两百字符，和输出多大无关。
真想留档的输出，写进文件（`Out-File` 或 `hands_write`），别指望从记忆里捞。

不想承担上面三条，就在 `config.json` 里设 `"transient_output": false`，回到整段入档。

### 8. 覆盖文件把别人的改动盖掉

**现象**　助手改了一个文件，几个小时后才发现是在一份过时的内容上改的；
中间别人（或另一个窗口）已经改过，改动被静默覆盖，无从找回。

**原因**　`hands_write` 直接 `writeFile`，既不留旧副本，
也不检查「我看到的版本还是不是现在这个版本」。

**修补**　两层：

- 覆盖或追加已有文件前，先把原始字节写到 `data/backups/<时间戳>-<sha前8>-<文件名>`，
  按 `backup_keep_days`（默认 30 天）和 `backup_max_bytes`（默认 1 GiB）自动清理，删最旧的。
  备份失败就中止写入，不假装已经留了退路。
- 支持 `expected_sha256`：给了就先比对当前文件哈希，不符直接拒写，并报出两边的前 12 位。
  读完文件、决定改之前，把读到的哈希带上。
### 9. 为了在命令里能直接调 `tsc`，改 `execFile` 的 env，结果 PowerShell 起不来

**现象**：改完之后每条命令都失败，报 `spawn powershell.exe ENOENT`。文件读写照常，只有跑命令全哑——`powershell.exe` 明明就在 `System32` 里。

**原因**：Windows 的环境变量名不区分大小写，但 Node 在 Windows 上把 `process.env` 的键保留成 `Path`（首字母大写）。我另起一个 `PATH` 键去覆盖，对象里于是同时有 `Path` 和 `PATH`；传给子进程的那一刻，PATH 只剩插件自己的 `bin` 目录，系统目录没了，连 exe 都搜不到。写文件、跑测试都不受影响，所以看着像“只有命令坏了”。

**修补**：不再碰 `execFile` 的 env。脚本第一行写 `$env:PATH = '<插件>\bin;' + $env:PATH`，在 PowerShell 内部前置，进程启动环境一行不动。同一个坑在宿主里也一样——要改 PATH 就改 `$env:PATH`，别改 `process.env`。
### 10. 外部程序的 UTF-8 输出被当成 GBK 读

**现象**　跑 `gh issue view`、`git log`、`node -e 'console.log("中文")'` 时，中文变成「鏆傛椂」「娴嬭瘯」这类字。把输出重定向进文件再读，还是那一串——看上去像 GitHub 或仓库里存坏了，其实是读的那一层坏了。

**原因**　这些程序往 stdout 写的是 UTF-8 字节。Windows PowerShell 5.1 接收原生命令输出时按 `[Console]::OutputEncoding` 解码，简体中文系统上是 GBK（936）。字节进入 PowerShell 的那一刻就已经转错，插件后面再怎么严格解 UTF-8 也救不回来——它拿到的已经是转错码的字符。

**修补**　在命令开头显式声明一次编码，让 PowerShell 按 UTF-8 收：

```
[Console]::OutputEncoding = [Text.Encoding]::UTF8
$OutputEncoding = [Text.Encoding]::UTF8
gh issue view 13 --json title
```

`[Console]::OutputEncoding` 管收，`$OutputEncoding` 管往原生命令送参数时的写法，两个都设才不会一边好一边坏。设在脚本里是一次性的，不影响这台机器上别的窗口。

插件本身**默认不改编码**，需要时自己把这两行写在命令开头。原因是改了会把所有命令的输出都当 UTF-8 读，`chcp 936` 环境下的一些老工具反而会坏——编码这件事，宁可让写命令的人明确声明。

### 11. 读完了、翻过头、文件是空的，看起来一模一样

**现象**　`hands_read` 传一个超过总行数的 `offset`，回来是一行正常的头部加空正文，退出码 0、不报错。
模型分不清"这个文件就这么点内容"还是"我翻错页了"；空文件和翻过头长得也一样。
头部只写「共 N 行」，不写在读哪一段，读到一半时看不出还剩多少。

**原因**　原先 `Math.max(0, Number(args?.offset ?? 0))` 把负数静默当 0，切完直接返回，
没有拿 `offset` 和 `lines.length` 比过。`lines.length > offset + limit` 只决定要不要加尾注，
越界的情况恰好没被这条覆盖。

**修补**　`offset` 必须是非负整数，负数和小数直接拒；`offset > 总行数` 报错并给出可用范围；
`offset === 总行数` 返回「已经在末尾」——那是合法的读完，不能当错误，否则「翻到空就停」的循环会被打断。
头部改成「第 a–b 行，共 N 行」，末尾写「还有 X 行没读，接着用 offset=b」。
空文件和文件不存在分开报。`hands_list` 的 `depth` 超上限不再静默截到 3，而是标注「已按 3 处理」。

**为什么值得改**　工具的返回形状本身就在教模型怎么用它。返回一个「看着正常、其实是空」的结果，
比直接报错更坏——报错会让人改姿势，空白只会让人以为读完了。

### 12. 读错没读错，看替换符和长度都看不出来

**现象**　用 `Get-Content` 读一份 UTF-8 的中文 JSON（不带 `-Encoding`），得到 10516 个字符，而正确读法是 10493。**长度反而变多了**，替换符（U+FFFD）一个都没有——可 `ConvertFrom-Json` 直接失败。反过来也成立：有时候解析过了，内容其实是错的。

**原因**　GBK 会把某些三字节的 UTF-8 中文字节序列解成「一个双字节字 + 一个落单字节」，字符数就漂了；而落单字节又被吞进下一个字符里，所以不产生替换符。两个最直觉的判断（有没有乱码字、长度对不对）因此都失效。

**修补**　三条：

1. **判断读对没读对，别数替换符、别比长度。** 拿两次读法（带 `-Encoding UTF8` 与不带）的结果做 `-eq` 比较，或者直接 `ConvertFrom-Json` 让解析器炸给你看。解析失败比长度异常更硬。
2. **读**：`Get-Content -Raw -Encoding UTF8`。这条只对「你确定对方是 UTF-8」成立；不确定就先看 BOM。
3. **写**：不要用 `Set-Content -Encoding utf8` —— PowerShell 5.1 的 `utf8` **一定带 BOM**（实测 15 字节的中文写出来是 20 字节，头 `EF BB BF`）。要无 BOM 只有一条路：

```
[IO.File]::WriteAllText($path, $text, (New-Object Text.UTF8Encoding($false)))
```

**顺便**：双重编码的「膨胀率」也不可靠。今早把 `publish.ts` 写坏那次是 23928 → 26231（1.10x），拿乱码结果再写回去只有 1.01x —— 两次都不显眼，但内容都坏了。所以写完必须**回读比对**，不能靠大小猜。

## 测试

```
node test/smoke.mjs      # 十三个用例：主体功能
node test/boundary.mjs   # 十一个用例：读文件的边界与报错
```

两个都不过宿主，直接加载插件本体。`smoke` 覆盖列目录、读文件、越界拒绝、`$` 不被展开、
中文不乱码、失败命令非零退出码、禁止项拦截、写入、写后核验、`hands_run` 正文当轮且回执不抄正文、
覆盖前留副本、expected_sha256 不符拒写、相符放行。

`boundary` 覆盖：正常读的头部格式、从中间读、offset 越界报错、offset 等于总行数不报错、
空文件、文件不存在、负数 offset、小数 offset、limit 为 0、depth 超限标注、depth 为 0。
